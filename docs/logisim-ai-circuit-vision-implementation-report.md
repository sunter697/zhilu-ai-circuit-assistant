# Logisim AI 电路图识别与自动重建模块说明报告

> 文档版本：`week1/1.0`  
> Vision IR：`vision-ir/0.1`  
> 完成日期：2026-10-24  
> 文档用途：项目说明书、课程设计/毕业设计正文、答辩 PPT、演示讲稿及完整版开发基线

## 1. 报告摘要

本项目在 Logisim Evolution 开源项目及其 AI 电路助手基础上，增加了“从电路图图片自动重建
可编辑电路”的能力。用户在 AI 助手中选择一张符合约束的 Logisim PNG，系统通过小型目标
检测模型识别元件，通过确定性图像算法提取导线并恢复连接关系，再使用版本化的 Vision IR
将识别结果传递给 Java。Java 在用户确认前完成协议、结构和拓扑校验，确认后才在工程中
创建新的标准 Logisim 电路；整个导入可以通过一次撤销完整恢复。

一周版不是把图片作为背景放进软件，也不是让大语言模型直接生成 `.circ` 文件。它实现了
一条可验证的纵向链路：

```text
PNG 图片 → 元件检测 → 导线/拓扑恢复 → Vision IR
→ Java 校验与规划 → 原生 Logisim 元件重建 → 用户确认 → 整体撤销
```

冻结版本支持输入/输出引脚、AND、OR、NOT、NAND、NOR 七类元件，以及浅色主题、ANSI
符号、原生缩放、全部朝右、单比特、正交且点到点的导线。系统采用“宁可拒绝，也不静默
导入错误电路”的安全策略。超出范围的多驱动、悬空、扇出和交叉导线会以结构化错误报告，
不会修改用户工程。

## 2. 项目背景与问题定义

传统 Logisim 电路必须由用户逐个放置元件和连接导线。已有 AI 助手可以理解文字需求并
操作电路，但图片输入包含两个不同问题：

1. **视觉感知问题**：图片中有哪些元件，它们位于哪里；
2. **电路语义问题**：每条导线连接哪些端口，哪个端口驱动信号，重建后是否与图片等价。

只完成元件框检测不能得到可仿真的电路。一个 AND 门即使类别和位置都正确，只要导线接到
错误端口，最终逻辑就会完全不同。因此，本模块把“拓扑正确性”和“失败时不破坏工程”放在
与模型精度同等重要的位置。

### 2.1 项目目标

- 从规范的 Logisim PNG 中识别元件、导线和连接关系；
- 将识别结果重建为真正的 Logisim 元件与 Wire，而不是静态图片；
- 重建结果可编辑、可仿真、可保存；
- 用户确认前不修改工程；
- 失败、取消、超时、协议不匹配时保持工程不变；
- 保留稳定接口，使一周版能够继续升级为完整版。

### 2.2 一周版设计原则

1. 视觉模型只负责感知，不直接修改工程；
2. Python 与 Java 之间只交换版本化 Vision IR；
3. 所有端口引用、网络和错误都必须可校验；
4. 默认创建新电路，不覆盖当前电路；
5. 整次导入只产生一个撤销动作；
6. 不确定或不支持的情况必须显式拒绝，不能猜测；
7. 优先完成稳定闭环，再扩展识别范围。

- XOR、XNOR；
- 一驱动多接收端的扇出；

- 深色主题、IEC 矩形门、任意缩放和元件旋转；
- 照片、手绘图、扫描件和其他电路软件的符号；
- 在图片上直接修改识别框和连线的审核界面；
- 不依赖 Python 的全 Java 发布运行时。

## 4. 总体架构

```text
┌─────────────────────────────────────────────────────────────────────┐
│                         Logisim AI 助手                              │
│  选择 PNG  ── 状态/取消 ── 识别摘要 ── 用户确认与编辑权限            │
└──────────────────────────────┬──────────────────────────────────────┘
                               │ 本机 HTTP
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│                      Python Vision Service                          │
│  输入校验 → 网格估计 → ONNX 元件检测 + 固定轮廓补偿                 │
│           → 绿色正交导线提取 → 端口匹配 → 拓扑约束检查               │
└──────────────────────────────┬──────────────────────────────────────┘
                               │ vision-ir/0.1
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│                       Java Import Pipeline                          │
│  协议校验 → IR 校验 → ERROR 拦截 → CircuitImportPlan               │
│           → 脱离工程构建 → 结构验证 → 新电路一次性应用               │
└─────────────────────────────────────────────────────────────────────┘
```

架构中的关键隔离边界是 Vision IR。Java 导入器不知道模型是 YOLO、模板匹配还是其他检测器；
Python 也不直接操作 Logisim 的内部对象。这使模型、导线算法和部署方式可以逐步替换，而不
需要推翻已经验证的导入核心。

## 5. 用户端完整工作流程

1. 用户启动 `vision-service\start_service.cmd`；
2. 服务加载冻结的 `models\best.onnx`，只监听 `127.0.0.1:8765`；
3. 用户在 AI 助手中点击“电路图”并选择 PNG；
4. Java 先调用 `/health` 检查服务、协议、模型和检测模式；
5. Java 通过 multipart 将图片字节上传到 `/recognize`；
6. Python 识别元件、导线和拓扑，返回 Vision IR；
7. Java 校验 IR，并拒绝所有 ERROR 级 `unresolved`；
8. Java 生成确定性的 `CircuitImportPlan`，此时工程仍未变化；
9. 界面显示元件数、net 数、警告、低置信度数量和目标电路名；
10. 用户允许本次会话编辑并确认；
11. Java 创建并验证新的 `Vision_Imported` 电路；
12. 软件切换到新电路，用户可以编辑、仿真或执行一次撤销。

## 6. 元件识别方案

### 6.1 小型模型的职责

训练后的模型只输出：

- 元件类别；
- 元件主体框；
- 检测置信度。

模型不直接预测导线、端口或 `.circ` 文件。端口位置由元件种类、尺寸、朝向和 Logisim
网格确定，导线则交给确定性算法处理。这种分工减少了模型输出空间，也让错误可以定位到
“元件感知”“端口匹配”或“拓扑组装”中的具体环节。

### 6.2 模型与训练配置

| 项目 | 冻结配置 |
|---|---|
| 模型 | YOLO11n 小型检测器 |
| 训练框架 | Ultralytics 8.4.158 |
| 训练 Python | 3.13 |
| 输入尺寸 | `1 × 3 × 800 × 800` |
| 类别数 | 7 |
| 类别 | INPUT_PIN、OUTPUT_PIN、AND、OR、NOT、NAND、NOR |
| 数据随机种子 | `20261021` |
| 正式样本数 | 2000 个唯一拓扑 |
| 划分 | 训练 1726、验证 274 |
| 训练上限 | 100 epoch，patience 20 |
| 实际结果 | 第 27 epoch 早停 |
| 部署格式 | ONNX，CPU 推理 |

正式数据按 `semanticHash` 分组，避免同一拓扑的不同图像变体同时进入训练集和验证集。
每个样本同时保存 PNG、YOLO 标签、Vision IR 真值和生成元数据。

### 6.3 模型域差异与补偿策略

模型在合成验证集上已经收敛，但真实 Logisim 截图的裁剪、符号相对尺寸和标签分布与训练图
存在明显差异。直接使用 ONNX 时，45 个真实门中正确命中 36 个，门召回约 80%，并有 5 个
额外误检，只有 10/20 图片的门类别与数量完全正确。

依据一周版止损规则，系统增加 `FixedScaleTemplateDetector`：在限定的浅色、ANSI、原生
缩放场景中，从黑色元件轮廓、尺寸和反相圆点恢复元件候选，并与 ONNX 结果合并。最终规则
包括：

- 同类重叠时保留校准后的固定轮廓几何，并采用较高置信度；
- 固定轮廓没有覆盖的高置信度 ONNX 元件可以加入；
- ONNX 高置信度引脚可以修正小尺寸 NOT/引脚的几何歧义；
- NAND/NOR 等门类别冲突时，保留在真实截图上校准过的固定轮廓类别。

该混合方案是限定场景补偿，不应描述成任意电路图的通用识别能力。

## 7. 导线与拓扑恢复

### 7.1 导线提取

导线提取器首先从背景灰色点阵估算网格间距和相位，然后按颜色阈值提取绿色像素。为避免
元件内部的绿色数值影响导线，算法遮挡元件主体内部区域，但保留端口附近的半格范围。

随后算法：

1. 在网格相邻点之间检测绿色水平或垂直覆盖率；
2. 将满足覆盖阈值的相邻网格点连接为图边；
3. 通过连通域搜索得到独立的 `wire region`；
4. 合并连续共线边，形成 Vision IR 中的正交线段；
5. 将元件模板推导出的端口吸附到对应网格节点；
6. 统计每个 wire region 连接的端口及端口方向。

### 7.2 一周版拓扑约束

一条可导入的 net 必须满足：

```text
恰好 1 个 OUTPUT 驱动端 + 恰好 1 个 INPUT 接收端
```

不满足时写入 ERROR 级 `unresolved`：

| 错误代码 | 含义 | 一周版行为 |
|---|---|---|
| `MULTIPLE_DRIVERS` | 同一连通域包含多个输出驱动端 | 拒绝导入 |
| `MISSING_DRIVER` | 连通域没有输出驱动端 | 拒绝导入 |
| `UNCONNECTED_WIRE` | 导线只到达一个元件端口 | 拒绝导入 |
| `UNCONNECTED_PORT` | 元件端口附近没有导线 | 拒绝导入 |
| `UNMATCHED_WIRE` | 导线没有连接任何元件端口 | 拒绝导入 |
| `UNSUPPORTED_FANOUT` | 一个驱动连接多个接收端 | 拒绝导入 |

### 7.3 T01–T20 为什么不能作为成功导入图

`tests/fixtures/real-logisim/T01` 至 `T20` 的目的，是评估真实截图中的元件类别和数量，
不是完整拓扑成功集。图片中的部分绿色线段存在共享主干、交叉接触、悬空或扇出。当前算法
只看图片像素连通性：横线和竖线只要在一个网格点接触，就属于同一 wire region。

例如 `T20_ALL_TYPES.png` 的多条输入线在图片中接触，最终 `wire_002` 同时包含 5 个输入
引脚的输出端口，因此稳定报告：

```text
MULTIPLE_DRIVERS: Wire region wire_002 has 5 drivers
```

这不是元件模型漏检，而是拓扑安全检查发现图片无法在一周版规则下可靠恢复。为避免生成
电气连接错误的电路，Java 会拒绝应用。成功导入演示必须使用 `tests/fixtures/day6/valid`
中的点到点图片。

## 8. Vision IR 中间协议

Vision IR 是识别端和重建端之间的稳定契约，版本固定为 `vision-ir/0.1`。主要字段包括：

| 字段 | 作用 |
|---|---|
| `schemaVersion` | 协议兼容性检查 |
| `source` | 图片 SHA-256、宽度和高度 |
| `profile` | 主题、门形状、网格、缩放和偏移 |
| `components` | 元件类型、框、锚点、属性、端口和置信度 |
| `nets` | 端点集合、正交线段、junction 和置信度 |
| `unresolved` | 无法安全确定的错误或警告 |
| `semanticHash` | 与布局无关的电路语义摘要 |

协议中保存视觉语义类型，例如 `AND`，而不保存 Java factory 类名。Java 通过映射将视觉
类型转换为 Logisim 原生元件，从而避免 Python 与 Java 内部实现耦合。

## 9. Java 重建与验证

Java 端由四个步骤组成：

### 9.1 IR 解析与校验

`VisionIrCodec` 将 JSON 转为 Java record，`VisionIrValidator` 检查：

- 协议版本；
- ID 唯一性；
- 坐标、框和置信度是否合法；
- 端口数量、端口方向和元件类型是否匹配；
- net endpoint 是否引用存在的元件与端口。

### 9.2 导入规划

`CircuitImportPlanner` 将图片坐标转换到 Logisim 网格，确定目标名称、元件属性和 Wire
线段。规划过程不修改用户工程，并会为重名电路生成 `Vision_Imported_2` 等安全名称。

### 9.3 脱离工程构建和结构验证

`CircuitImportBuilder` 先构建一个尚未加入项目的电路。`StructuralImportVerifier` 对真实
创建出的组件、锚点、端口和 Wire 进行复查。只有构建和验证均成功，才允许进入应用步骤。

### 9.4 一次性应用与撤销

最终通过 Logisim 原有项目动作机制加入新电路。整次图片导入只有一个项目动作，因此用户
执行一次撤销即可删除所有新建元件、导线和电路，不会留下半完成状态。

## 10. Python 与 Java 通信

一周版采用本机 HTTP：

| 接口 | 作用 |
|---|---|
| `GET /health` | 返回状态、服务版本、协议版本、模型摘要和检测模式 |
| `POST /recognize` | 接收字段名为 `image` 的 PNG multipart，返回 Vision IR |

安全限制包括：

- 服务只绑定 `127.0.0.1`、`localhost` 或 `::1`；
- Java 客户端拒绝非环回 HTTP 地址；
- 图片文件最大 10 MiB；
- 图片尺寸最大 4096 × 4096；
- Java 连接超时 2 秒、健康检查 3 秒、识别请求 30 秒；
- 服务运行时拒绝第二个 8765 实例，关闭后可以立即重启；
- 服务错误使用结构化错误码，不把任意异常直接暴露给 UI。

选择 HTTP 的原因是开发周期短、Python 视觉生态成熟、进程隔离清晰且容易调试。它不是
Java 与 Python 唯一的通信方式。完整版将保留 Python 服务作为基准实现，并逐步加入 Java
ONNX Runtime，使普通用户不再需要单独启动 Python。

## 11. AI 助手集成与错误安全

图片识别入口位于原有 AI 助手输入区。识别任务在后台线程运行，避免阻塞 Swing 界面。
用户可以在识别阶段取消。识别完成后，界面显示摘要；只有“允许本次会话编辑”已开启且
用户再次确认时，Java 才会创建新电路。

下列路径都经过“工程电路数量保持不变”的自动测试：

- 本机服务未启动；
- HTTP 连接或识别超时；
- 用户取消；
- Vision IR 协议不匹配；
- JSON 或 IR 结构无效；
- `unresolved` 中存在 ERROR；
- 识别期间用户切换了目标工程；
- 用户没有授予本次会话编辑权限。

这种设计把 AI 助手定位为交互和解释入口，而不是绕过验证直接修改电路的执行者。

## 16. 一周版的价值与可用于答辩的技术特点

### 16.1 从“识别元件”扩展到“重建可执行电路”

项目输出不是框和标签，而是 Logisim 原生组件、Wire 和 netlist。重建结果能够继续编辑、
仿真和保存，完成了从视觉结果到工程对象的转换。

### 16.2 学习模型与确定性算法结合

目标检测擅长识别元件，网格、导线和端口约束则更适合确定性算法。混合架构比让单一模型
直接生成全部电路结构更容易验证和调试。

### 16.3 版本化中间表示

Vision IR 将 Python 感知与 Java 重建解耦。它既是通信协议，也是测试接口、错误载体和
完整版演进边界。

### 16.4 错误安全和整体撤销

系统把失败路径作为核心功能：识别期间零修改、应用前验证、错误不导入、一次撤销。这比
单纯展示一次成功识别更符合实际软件工程要求。

### 16.5 可重复实验

数据生成、随机种子、模型摘要、依赖版本、回归图和演示顺序全部被冻结，测试结果能够在
同一环境中重复验证。

## 17. 已知不足与结果解释边界

1. 真实图片集参与过固定轮廓阈值校准，尚缺独立留出集；
2. T01–T20 是元件回归图，不是成功拓扑导入集；
3. 像素连通算法暂时无法区分交叉但不连接与 junction；
4. 一周版为降低错误风险，尚未接受合法扇出；
5. Python 服务增加了安装和启动步骤；
6. 固定轮廓补偿只适用于受限的原生 Logisim 风格；
7. 用户只能接受或拒绝结果，还不能在覆盖层上修改错误元件和连接；
8. 当前指标证明冻结场景的稳定性，不能外推到照片、手绘或任意电路图。

答辩中应明确这些限制。准确说明适用范围不会削弱项目价值，反而能够体现对数据泄漏、域
差异、拓扑安全和评估有效性的理解。

## 30. 完整版阶段 C 拓扑恢复记录（2026-10-25）

## 31. 完整版阶段 D 识别审核第一增量（2026-10-25）

原有图片导入流程只在识别完成后显示元件数、网络数和警告数，用户无法判断元件框、导线或
junction 是否贴合原图。本增量把简单确认框替换为模态审核窗口，但不改变“确认前工程零
修改”的安全边界。

审核窗口完成以下能力：

- 显示本次识别使用的原始 PNG，并按图片坐标叠加 Vision IR；
- 使用绿色框显示普通元件，橙色显示低置信度元件或网络；
- 使用蓝色显示网络线段、红色显示端口与锚点、紫色显示 junction；
- 元件、导线和 junction 三类覆盖层可独立开关，便于观察被遮挡细节；
- 右侧集中显示服务警告、低置信度元件和低置信度网络；
- 显示检测方式、目标电路名和识别统计，只有点击“导入电路”才继续原有构建流程；
- 预览前重新读取文件并核对尺寸；服务返回标准 64 位 SHA-256 时还会核对内容哈希，因此
  识别完成后被同尺寸文件替换也会被拒绝；
- 图片无法读取、尺寸变化或哈希变化时不允许导入，工程保持不变。

`PreparedImport` 现在同时保存源图片路径和经校验的 Vision IR，规划结果仍由
`CircuitImportPlanner` 产生。覆盖层本身只负责显示，不直接修改 IR 或 Logisim 工程。本轮
测试覆盖离屏绘制、三类图层开关、尺寸变化和同尺寸内容替换，并继续通过控制器与助手面板
回归。下一增量只允许修正拓扑兼容的门类型或标签，每次修正后必须重新规划并通过结构校验，
不会允许用户在覆盖层上任意拖线后绕过安全检查。

## 32. 完整版阶段 D 人工修正增量（2026-10-25）

审核窗口新增“修正”页。用户可以把多输入组合逻辑门在 AND、OR、NAND、NOR、XOR、
XNOR 六种类型之间修正，也可以重命名输入、输出引脚；NOT、引脚方向、元件坐标、连线、
junction 和端口归属仍不可手工修改。这个限制使人工操作只改变元件语义，不允许绕过拓扑
识别与结构校验。

点击“导入电路”后不会直接使用界面字段构建电路，而是依次执行：

1. 校验元件 ID、可修改类型、标签长度和控制字符；
2. 复制原 Vision IR，生成新的修正版 IR，并清除已不再适用的原语义哈希；
3. 通过真实 Logisim 元件工厂重新计算每个端口；
4. 当门类型导致端口位置变化时，只把原来终止于该端口的线段末端迁移到新端口；
5. 重新检查正交导线、端口全连接、单驱动、网络互斥、元件重叠和导线穿越元件；
6. 生成新的 `CircuitImportPlan`，最后仍以一个可撤销动作创建新电路。

例如 AND 改为 XOR 时，Logisim 的 XOR 输入端会比 AND 输入端向左移动 10 个坐标单位。
第一版实现因原导线不再终止于端口而被结构校验正确拒绝；随后加入受约束的端点迁移，修正
后的导线会落到 XOR 的真实输入端，且仍需通过所有网络和几何规则。若迁移造成斜线、短路、
穿越元件或其他冲突，修正会在审核窗口内报错，工程保持不变。

自动测试覆盖安全门类型修正、引脚重命名、端口位置迁移、重复标签、未知元件、引脚方向
改变、AND→NOT 等不安全改型，以及修正后导入与一次撤销。阶段 D 至此完成：识别预览、
风险提示、有限人工修正、重新规划、重新校验和确认后导入已经形成闭环。

## 34. 完整版阶段 E 嵌入式 Java 识别链路（2026-10-26）

本增量把原生 v0.4 图片的生产识别链路从 Python 进程迁入 Java。`OrthogonalWireExtractor`
直接在 `BufferedImage` 上联合提取黑色导线和蓝色引脚引线，清除元件主体轮廓，再把像素覆盖率
投影到 10 像素、零相位网格。`NativeCircuitTopologyRecognizer` 负责端口几何、连通区域、
单驱动检查、非端口短枝裁剪、扇出 junction、线段合并和 Vision IR 组装。算法仍会把多驱动、
无驱动、孤立端口和无法归属的长导线作为 unresolved error，而不会猜测后继续导入。

迁移验证分为两层：

1. 使用 4 张 native-v04 固定图片和真值元件框，Java 与 Python 在元件端口、网络端点、
   junction 和 Python 生成的语义哈希上逐项一致；
2. 使用正式 `best.onnx` 从图片开始执行 Java 检测、导线提取和拓扑组装，4/4 图片的元件、
   端口、网络和 junction 与冻结真值一致。

由于正式九分类模型在冻结 200 张原生图片上的元件检测已经达到 200/200 exact image，原生
配置不再需要复制 Python 的模板补偿器。旧绿色截图仍由原 HTTP 服务兼容；这是一条明确的
配置边界，不把两个外观域混成一个未经验证的 Java 路径。

## 39. 多尺寸与多缩放识别增量（2026-10-28）

树，从而删除重采样文字形成的闭环而不改变电气连通关系。原始 100% 冻结图和 Java 关键边界
样本均继续通过，防止缩放修复破坏既有路径。

## 41. Java 导入端的非连接交叉处理（2026-10-28）

full-v09 已能正确区分“带 junction 的连接”与“没有圆点的普通交叉”，但首次在软件界面
导入 T18、T19、T20 时仍出现 `Separate nets ... touch or cross`。复查 HTTP 返回的 Vision IR
表明三张图的元件、端点图和 unresolved 均正确；失败发生在 Java 导入规划阶段，而不是模型
检测阶段。进一步检查 Logisim 的 `CircuitWires` 和 `WireRepair` 后确认：两条连续 Wire 在
线段中部垂直相交时不会连接；只有端点落在另一条线段上、两个端点相接或同轴线段重叠时，
WireRepair 才会拆分、合并并形成电气连接。原规划器只做了几何相交判断，因而把安全的普通
十字交叉误判成短接。

最终方案保留识别得到的元件、端口、导线和网络端点图。规划器区分“纯中段十字交叉”和
“会真实导通的接触”：前者直接保留原 Wire，因此布局与识别预览一致；后者才启用 Logisim
原生 Tunnel，而且只替换冲突网络中端点较少的一条，其他网络继续保留普通导线。同一网络的
Tunnel 使用相同内部标签，不同网络使用不同标签；位宽、方向和位置全部写入不可变导入计划，
并由结构校验器逐项核对。这样既避免静默短接，也避免把整张图变成 Tunnel 标签堆叠。

验证包括三层：人工构造的中段十字交叉保留原导线且通过 AND 真值表；人工构造的端点接触
只为一个冲突网络创建两个 Tunnel，同样通过真值表；全部 AI Java 回归通过。在本机
`full-v09/0.1`、正式 `best.onnx` 和 HTTP 模式下，T18（8 元件/7 网络）、T19（10/9）和
T20（13/12）均完成识别、规划、结构校验和加入工程，并明确断言三张图均保留原导线、生成
0 个 Tunnel。该修复只改变 Java 导入判定，不改变 ONNX 权重、Vision IR 协议或 full-v09
的识别评估结果。
